## Executed through-line

P3.4 proves this serialized artifact boundary:

`natural-language goal -> live discovery -> verified DiscoveryTrace -> deterministic builder ->
validator -> store -> destroy discovery state -> load -> fresh model-free replay -> verified result`

The live acceptance uses the exact required goal, `Find the savings balance for member 67890.`,
and the trusted authoring metadata already accepted in P3.3. That metadata requires:

- one required sensitive `member_id` string input;
- fill `member.search.member_id` from `InputValueRef("member_id")`;
- clicks for Search, member result, and Savings account in discovered order;
- success conditions for member identity, literal account type `Savings`, and visible balance;
- parsed `balance_minor_units` and `currency` outputs;
- the `MEMBER_NOT_FOUND` business outcome;
- a three-observation, 400 ms Search postcondition retry.

The same trusted success-template metadata supplies Discovery's required completion target tuple:
`member.details.identity`, `member.account.type`, and `member.account.balance`. This does not encode
an action sequence. It only prevents Discovery from accepting `COMPLETE` until the model cites
current evidence for every required semantic fact.

## Blocker and correction

The first P3.4 attempt returned a valid Discovery `SUCCESS` with identity and balance evidence but
without account-type evidence. The unchanged Builder correctly rejected it with
`BUILD_COMPLETION_EVIDENCE_MISSING`.

The correction added default-empty trusted `required_completion_targets` to `DiscoveryRequest`.
Discovery now presents those target names to the model, verifies each cited value against the latest
snapshot, repairs an incomplete `COMPLETE` without another UI action, and rejects profile-unknown
requirements before model or gateway work. Builder validation was not weakened, and no workflow or
application rule was added to Discovery.
