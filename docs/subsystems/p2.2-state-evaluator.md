## Purpose and boundary

`StateEvaluator` interprets an immutable `EvaluationSnapshot` of semantic targets against a `CapabilityDefinition` and runtime inputs. It does not collect observations, execute actions, call a model, persist evidence, or perform retries.

```
EvaluationSnapshot
      |
StateEvaluator
  | conditions
  | terminal state
  ` outputs
```

The snapshot distinguishes an unobserved target from an explicitly `NOT_VISIBLE` or `UNAVAILABLE` target. It contains only semantic target references, target state, and bounded text; it has no DOM, browser, or provider handle.

## Contract and behavior

Conditions return `TRUE`, `FALSE`, or `UNKNOWN`. A visible target makes `TargetVisible` true; a not-visible target makes it false; an unavailable or unobserved target is unknown. Text comparisons trim both sides, then compare exactly or by literal containment. There is no case folding, punctuation removal, fuzzy matching, or model interpretation.

Missing runtime inputs return an `UNKNOWN` condition with `RUNTIME_INPUT_MISSING`; diagnostic summaries identify only the input name, not its value. Evaluation performs no persistence.

All declared success conditions must be true for success. A false identity condition prevents success even when a balance parses successfully. Declared business outcomes are expected terminal states, not evaluator failures. Multiple true outcomes, or a true success and a true outcome, produce `CONFLICT` with `TERMINAL_STATE_CONFLICT`.

Outputs are extracted separately from terminal classification. `currency_minor_units` accepts non-negative USD-style amounts with exactly two decimals, optional `$`, correctly grouped commas, and an optional trailing uppercase ISO currency code. It uses `Decimal` and returns an integer minor-unit value. `currency_code` accepts an uppercase ISO code alone or trailing after whitespace. Malformed, missing, unavailable, or type-incompatible outputs return typed issues; no fallback value is invented.

## Alternatives and costs

Letting Replay Engine inspect page text directly would mix surface execution and interpretation, making state/error behavior brittle. Asking a model whether a goal succeeded would violate deterministic replay. The selected boundary instead requires separate snapshot collection and only supports the deliberately small condition/parser vocabulary. New business states or parsing formats require explicit contract changes.

## Tests and limits

Focused tests cover tri-state conditions, in-memory input resolution, sensitive-value-safe diagnostics, false-success prevention, expected business outcomes, terminal conflicts, output parsing, output failures, ordering stability, and immutability. The real development fixture is evaluated for both success and `MEMBER_NOT_FOUND`.

P2.2 does not collect snapshots from a `SurfaceAdapter`, verify live profile bindings, execute steps, validate invocation inputs, or implement replay/retry behavior. Those integrations remain P2.3 or later.
