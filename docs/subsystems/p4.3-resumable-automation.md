## Before implementation

### 1. Problem

P4.2 ended safely at `resume_requested`. P4.3 closes only the remaining lifecycle gap: preserve a
definitely-not-executed Replay step, route the same live session through human action, validate
fresh current state, restore automation with a new generation, and let Replay finish without
repeating earlier side effects.

### 2. Input and output contract

`ReplayCheckpoint` identifies the capability/version, blocked step ID and zero-based index,
`APPROVAL_REQUIRED` reason, `NOT_EXECUTED` effect state, and suspended control generation. It holds
no browser handle, surface reference, runtime value, model data, or reusable artifact state.

`ReplayResult.checkpoint` is optional and remains absent for all non-resumable failures.
`ReplayContinuationResult` reports intervention, validation, resumed Replay, generation, terminal,
and already-consumed outcomes without exposing protected runtime inputs.

### 3. State and dependencies

`ReplayContinuationRegistry` owns process-local pending invocation state. Runtime input values are
held only as `SecretStr` values in repr-hidden fields and are removed when a continuation is
consumed or terminally stopped. A per-continuation `asyncio.Lock` provides exactly-once resume
consumption.

`ReplayContinuationCoordinator` depends on Replay and the existing Intervention Manager interface.
It performs no surface action, browser interpretation, model call, ownership mutation, or policy
decision. Session Controller remains authoritative for state, owner, dispatch serialization, and
generation.

### 4. Accepted direction

The implemented flow is:

`Replay -> APPROVAL_REQUIRED -> immutable safe checkpoint -> Intervention Manager -> existing
P4.2 HTTP console -> Operator Action Gateway -> same surface session -> return control -> fresh
Replay semantic validation -> P4.1 automation restoration/new generation -> Replay.resume ->
fresh terminal/postcondition evaluation -> terminal result or one new bounded intervention`

This applies ADR-001, ADR-002, ADR-003, and ADR-006 without changing frozen P4.1/P4.2 behavior.

### 5. Alternatives considered

Restarting Replay from step 1 was rejected because it duplicates prior side effects. A second loop
inside the coordinator was rejected because Replay owns deterministic interpretation. Treating a
matching human action target as completion was rejected because current application state, not
action identity, is authoritative.

The selected seam adds `ReplayEngine.resume(...)` and shares one internal execution loop with
ordinary replay. Resume observes current state before dispatch: terminal state wins; otherwise a
true deterministic blocked-step postcondition advances past the step, a false postcondition may
re-enter it under normal policy, and unknown or absent proof fails without dispatch.

### 6. Costs and failure modes

Continuation is in-memory and process-local. It does not survive process or browser failure and is
not a durable workflow system. P4.3 supports only `APPROVAL_REQUIRED`; no generalized recovery
language or Discovery continuation is implemented.

Repeated approval creates one new intervention and returns to the caller; it never loops
automatically and never weakens policy. An action with uncertain effect, including
`ACTION_EFFECT_OCCURRED_EVIDENCE_FAILED`, receives no checkpoint and cannot be automatically
retried. A capability with neither terminal proof nor a blocked-step postcondition remains safely
unverified after handback.

### 7. Boundary and assumption tests

Tests cover approval-only checkpoint creation, checkpoint identity, sensitive repr/evidence,
uncertain effects, same-session intervention, fresh validation, G2 context use, stale G1 rejection,
fresh terminal success, postcondition advancement, no-fix behavior, bounded repeated approval,
terminal stop, event-driven concurrent resume, no earlier action repetition, and forbidden model,
provider, browser-adapter, or direct surface-action dependencies.

## After implementation

### 8. Actual files and behavior

- `src/capability_runner/contracts/replay.py` adds immutable `ReplayCheckpoint` and an optional
  checkpoint on `ReplayResult`.
- `src/capability_runner/contracts/continuation.py` adds the safe orchestration result.
- `src/capability_runner/replay/replay_engine.py` emits checkpoints only for pre-dispatch approval,
  provides read-only fresh resume validation, and resumes through the original execution loop.
- `src/capability_runner/application/run_coordinator.py` stores masked in-memory invocation state,
  adapts Replay validation to P4.1, requests interventions, consumes resume once, supplies the new
  generation, and creates at most one follow-up intervention for repeated approval.
- `tests/unit/replay/test_replay_engine.py` covers checkpoint and fresh-state cursor semantics.
- `tests/unit/application/test_run_coordinator.py` covers lifecycle, privacy, stop, repeat, and race
  behavior against the real frozen Session Controller and Intervention Manager.
- `tests/end_to_end/test_replay_intervention_resume.py` covers the complete real-browser flow
  through the existing P4.2 HTTP API.
- `tests/architecture/test_dependency_boundaries.py` prevents model/provider/concrete browser
  imports and direct `perform_action` calls in the continuation coordinator.

Savings request returned approval before surface execution. The operator clicked Savings once
through P4.2 HTTP and Operator Action Gateway. After return, Replay collected fresh semantic state,
extracted `balance_minor_units=98765` and `currency=USD`, and dispatched no additional action.

### 10. Known limits and next integration

The continuation registry is local, in-memory, and single-process. Crash recovery, durable queues,
distributed leases, remote operator authentication, and generalized failure recovery are out of
scope. A blocked step without deterministic postcondition proof cannot be advanced unless current
terminal conditions already resolve the capability. Only `APPROVAL_REQUIRED` is resumable.

No coordinator-specific evidence vocabulary was added. Existing Action Gateway, Operator Action
Gateway, and Intervention Manager events preserve the accepted correlated action and handoff
record without duplicating evidence. A later evidence-schema milestone may add explicit
`REPLAY_SUSPENDED`/`REPLAY_RESUMED` events after separate approval.
