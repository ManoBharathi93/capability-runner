# Subsystem: Capability Builder

## Status

- Design: **ACCEPTED BASELINE**
- Implementation: implemented
- Verification: passed
- Authorized milestone: P3.3

## Purpose and boundary

`CapabilityBuilder` deterministically compiles a verified successful `DiscoveryResult` and trusted
authoring metadata into the existing schema-version-1 `CapabilityDefinition`. It then passes that
definition through `CapabilityValidator`; the caller may publish the returned
`ValidatedCapability` through `CapabilityStore`.

The complete authorized path is:

`natural-language goal -> real discovery -> verified DiscoveryTrace -> CapabilityBuilder ->
CapabilityDefinition -> CapabilityValidator -> CapabilityStore`

P3.3 stops after immutable local storage. It does not replay the generated artifact and P3.4 has not
started.

## Trust model

Discovery supplies only validated, non-raw provenance:

- ordered semantic `fill` and `click` actions;
- explicit Action Gateway execution outcomes;
- fill-value positions inside the original goal, not fill values;
- structural observation fingerprints without observed text;
- completion text fingerprints and verified identity-to-fill relationships.

The builder derives only facts justified by that provenance:

- required `STRING` inputs from executed goal-span fills;
- input names from semantic target names;
- ordered action templates;
- deterministic semantic step IDs and duplicate ordinals;
- input references linking fills and identity conditions.

Trusted `CapabilityBuildRequest` metadata supplies facts that execution cannot safely infer:

- capability identity, version, name, and description;
- application requirement;
- input sensitivity;
- reusable success semantics, including fixed literals;
- output names, types, sources, and parsers;
- business outcome rules;
- step preconditions, postconditions, and retry policies.

A trusted literal success condition is accepted only when its SHA-256 fingerprint matches current
verified completion evidence. Output source targets must also have verified completion evidence.
The builder rejects unsuccessful or internally inconsistent traces and never copies raw goals,
model responses, observations, invocation values, fingerprints, provider identity, selectors,
browser details, or run identifiers into an artifact.

## Dependencies and state

`CapabilityBuilder` owns no mutable state and performs no I/O. It depends only on typed contracts and
`CapabilityValidator`. It makes zero model or provider calls and imports neither discovery runtime
code, `ModelClient`, provider adapters, `BrowserSurfaceAdapter`, nor Playwright. Storage remains a
separate caller-owned operation through `CapabilityStore`.

This applies ADR-004 without changing the accepted capability schema, Discovery behavior, Replay
behavior, provider composition, or browser mechanics. No dependency was added.

## Alternatives and costs

Copying raw traces into an artifact was rejected because it would persist invocation-specific and
potentially sensitive data. Asking a model to author the artifact was rejected because output would
not be deterministic and would couple reusable execution to a provider. Inferring outputs, business
outcomes, or retry policy from observed text was rejected because one successful run does not prove
those reusable semantics.

The selected boundary requires explicit trusted metadata. It also requires discovery completion to
cite every target used by a success template or output. This is intentionally conservative: a valid
browser outcome with insufficient retained evidence cannot be compiled into a richer claim.

## Implemented files and behavior

- `src/capability_runner/contracts/discovery.py` retains immutable non-raw action provenance and
  verified completion relationships.
- `src/capability_runner/discovery/discovery_engine.py` produces that provenance without changing
  its action selection, dispatch, completion, or stopping behavior.
- `src/capability_runner/contracts/capability_building.py` defines frozen trusted build metadata.
- `src/capability_runner/capabilities/capability_builder.py` performs deterministic compilation and
  validation.
- Unit tests cover rejection, derivation, ordering, deterministic IDs, metadata handling,
  redaction, validator invocation, reference semantics, and cross-run artifact equality.
- Integration tests cover build, validation, immutable save, load, and duplicate-version rejection.
- Architecture tests prohibit model, provider, browser, Playwright, and application-specific
  dependencies in the builder.

## Known limits and next integration

P3.3 proves deterministic compilation and immutable publication for the authorized read-only flow.
It does not prove generated-artifact replay, cross-provider discovery parity, arbitrary application
semantics, schema migration, or automated authoring of trusted metadata. Fresh-session replay of the
generated artifact is P3.4 and remains not started.
