# Subsystem: Live Discovery Engine

## Status

- Design: **ACCEPTED BASELINE**
- Implementation: implemented
- Verification: passed
- Authorized milestone: P3.2

## Purpose and boundary

`DiscoveryEngine` runs a bounded observe-decide-act loop from a natural-language goal. It receives
the provider-neutral `ModelClient`, an `ActionGateway`, and a semantic snapshot collector through
injected interfaces. It imports neither concrete provider adapters nor Playwright.

The engine does not build, validate, or store capability artifacts. Trusted callers may require a
bounded list of semantic targets to appear in verified completion evidence when preparing a trace
for later artifact construction. Replay semantics are unchanged.

## Trust model

The goal, page text, and every model response are untrusted. The model may propose only one of four
strict decisions: `ACT`, `COMPLETE`, `REQUEST_INTERVENTION`, or `FAIL`. `ACT` is limited to semantic
`fill` and `click` operations. Selectors, URLs, code, browser handles, policy changes, unknown fields,
unknown targets, and fill values not copied exactly from the goal are rejected before dispatch.

Trusted authority remains outside the model:

- `ApplicationProfile` defines the allowed semantic target vocabulary.
- `DiscoveryRequest.required_completion_targets` defines trusted semantic facts that must be cited
  before completion; its default is empty for backward compatibility.
- `DiscoveryEngine` enforces strict parsing, grounding, and stopping limits.
- `ActionGateway`, `PolicyGuard`, and `SessionController` authorize and serialize every side effect.
- Current semantic observations, not model assertions, validate completion evidence.
- `EvidenceRecorder` persists only the existing allowlisted gateway events with fill-value redaction.

## Observation and stopping behavior

`DiscoverySnapshotCollector` inspects trusted bindings without exposing locators or browser handles.
Ambiguous or temporarily uninspectable entries are presented as `UNAVAILABLE`; this permits broad
discovery observation while the gateway and adapter still fail closed if an unavailable target is
selected. Presentation is stable-sorted and bounded to 24 targets, 256 characters per visible text,
and 4,000 goal characters.

The loop permits at most 12 turns, 8 dispatched actions, and 2 invalid model responses. A repeated
identical action against an unchanged snapshot stops as `NO_PROGRESS`. Policy denial stops as a
failure, approval routes to intervention, and an uncertain action effect stops for intervention
without retrying the side effect.

`COMPLETE` is accepted only when every cited target is trusted, visible in the latest snapshot, and
has exact current text. At least one cited value must occur exactly in the goal, grounding completion
to the requested identity. When trusted required completion targets are present, every target must
also appear in the verified evidence set. Missing evidence produces the repairable
`COMPLETION_EVIDENCE_MISSING` result without a browser side effect; a required target absent from
the trusted profile fails before observation, model invocation, or action dispatch. The model sees
only the required semantic target names, not Builder templates, parsers, policies, or selectors.
Raw model responses, goals, fill values, and observed text are not copied into the returned trace.

## Live evidence

On 2026-09-12, the configured Gemma-compatible model passed the neutral `ModelClient` smoke probe.
The same configured model then drove real Chromium sessions through the real CoreBank profile,
Action Gateway, Policy Guard, Session Controller, Browser Surface Adapter, and Evidence Recorder:

- case `67890`: success in 5 turns and 4 actions; current browser state independently confirmed
  `$987.65 USD`;
- case `12345`: success in 5 turns and 4 actions in a fresh browser/control session; current browser
  state independently confirmed `$4,382.21 USD`.

P3.4 subsequently exercised the exact goal `Find the savings balance for member 67890.` with
trusted required evidence for identity, account type, and balance. Discovery returned all three
verified targets in 5 model calls and 4 gateway actions, allowing the unchanged Builder to compile
the trace.

The live tests are marked `live` and excluded from ordinary pytest runs. They load local ignored
configuration without printing credentials or endpoint data. Normal tests use deterministic fakes
and make no provider network calls.

## Limitations

P3.2 proves bounded discovery for the authorized read-only synthetic flow. Required completion
targets state which current semantic facts must be evidenced, not their expected values, action
sequence, selectors, or workflow. It does not prove cross-provider parity, arbitrary-goal semantic
verification, production prompt-injection immunity, or human handoff.
