# Subsystem: P4.2 Minimal Operator Console

## The original controlled operator interface

This record describes the earlier HTTP/semantic-action console. That controlled path remains useful for tests; the product now uses direct input in the managed browser.

For current behavior, use [the product guide](../submission/test-product.md) and
[progress](../progress.md). The record below preserves the decision, tests and
limits at this subsystem's implementation date. Earlier phase restrictions and
operator-control descriptions are historical; the
[native handoff record](direct-browser-handoff.md) explains the later physical-input exception.

## Before implementation

### 1. Problem

A local human operator needs a thin view/controller over the P4.1 handoff: see why automation
stopped, inspect the current browser, issue explicit typed semantic actions against that same live
session, and return control without claiming that automation has resumed.

### 2. Input and output contract

The public route is `/operator/interventions/{intervention_id}`. JSON endpoints expose safe status,
currently visible registered controls, typed `fill`/`click` action results, return-control results,
and stop results. The visual endpoint returns a bounded `image/png` response.

`OperatorActionSubmission` accepts only `semantic_target`, `action_kind`, and an optional secret
`value`. Extra fields are forbidden. A fill requires a non-empty value; click rejects a value. The
client cannot submit a surface reference, selector, locator, generation, operator ID, profile, raw
navigation, script, coordinates, file, or arbitrary action kind.

### 3. State and dependencies

`OperatorConsoleService` owns only immutable local registrations that bind one intervention record
to a trusted profile, local operator identity, and allowlisted presentation controls. P4.1 remains
authoritative for intervention records, ownership, generation, dispatch serialization, and action
evidence.

The application service depends on P4.1 interfaces, Session Controller reads, trusted contracts,
target inspection, and the read-only `SurfaceViewProvider`. The Flask adapter depends only on that
application service and transport contracts. Neither layer imports Playwright, Browser Surface
Adapter, Discovery, Replay, Model Client, or provider modules.

### 4. Accepted direction

ADR-003 requires operator mutations to pass through the shared gateway controls. ADR-006 requires
the Operator Interface to bind to the existing managed session and return explicitly. The
implemented path is:

`operator browser -> intervention HTTP API -> OperatorConsoleService -> OperatorActionGateway ->
SessionController.operator_dispatch -> SurfaceAdapter -> same SurfaceSessionRef`

The HTTP action route contains no `perform_action` call. It resolves all trusted execution context
server-side from the registered `InterventionRecord`.

### 5. Alternatives considered

A React build was not selected because the product frontend is optional P5.4 polish and one local page does not
justify a second toolchain. A direct browser/CDP attachment was not selected because it would
bypass typed actions and policy. Adding screenshot capture to the existing action adapter protocol
was not selected because it would widen every existing implementation and test double; a separate
read-only visual port keeps the capability explicit.

### 6. Costs and failure modes

The console is local/demo scoped and has no authentication, tenant authorization, remote exposure,
durable registration, reconnect recovery, or multi-process coordination. Production use would
require authenticated operator identity plus tenant/session authorization. The server-side
intervention/session binding remains enforced even in local mode.

PNG views can contain synthetic on-screen values. They are ephemeral HTTP responses with
`Cache-Control: no-store`; they are not recorded as evidence or written to the filesystem. P4.2
does not claim screenshot redaction. Capture is capped at 1600 by 1200 pixels and 2 MB. An
unavailable or mismatched view fails with a safe status and no browser handle or adapter exception.

### 7. Boundary and assumption tests

Tests cover strict request rejection, unknown interventions, server-side session binding, current
ownership, visible-control filtering, exact gateway delegation, redaction, return/stop behavior,
closed sessions, bounded in-memory views, architecture imports, absence of direct surface action
calls, real HTTP, real Chromium, and rendered-page operation.

## After implementation

### 8. Actual files and behavior

- `src/capability_runner/contracts/operator_console.py` defines strict safe API contracts.
- `src/capability_runner/contracts/surfaces.py` defines immutable bounded `SurfaceView` data.
- `src/capability_runner/surfaces/surface_view.py` defines the generic read-only visual port.
- `src/capability_runner/surfaces/browser_surface_adapter.py` captures an in-memory bounded PNG
  from the existing page for the supplied opaque session reference.
- `src/capability_runner/application/operator_console.py` binds trusted intervention/profile/
  operator/control data, filters controls by current target visibility, delegates actions exactly
  once to Operator Action Gateway, and delegates handback/stop to Intervention Manager.
- `src/capability_runner/interfaces/async_core_runner.py` keeps async browser/core work on one
  persistent event loop behind synchronous Flask requests.
- `src/capability_runner/interfaces/operator_http.py` exposes the page and five narrow API routes.
- `src/capability_runner/interfaces/templates/operator_intervention.html` is the single local page
  with status, reason, live preview, semantic fill/click controls, refresh, return, and stop.

Available controls are an operator-composition allowlist intersected with trusted profile bindings
and current `VISIBLE` target inspection. Application-specific labels live in composition data, not
generic surface contracts. Fill values use `SecretStr`, are cleared in the page after submission,
and are absent from response JSON and persisted evidence.

The view and controls are available only while the registered operator owns the session. Return
control invokes P4.1 and stops at `resume_requested`, shown as `Resume validation required`.
P4.2 never invokes the resume validator, Discovery, or Replay.

### 10. Known limits and next integration

There is no production authentication, authorization transport, TLS, CSRF protection, durable
console registry, browser reconnect, remote co-browsing, screenshot masking, or final React product
shell. The local page is intentionally dependency-light and is created by an injected Flask app
factory; live run composition supplies the already-created intervention, profile, and operator.

P4.3 automatic Discovery/Replay continuation is not implemented. Return control ends at
`resume_requested`; a later separately authorized coordinator may perform fresh validation and
continue the owning engine. P2, P3, and P4.1 remain frozen.
